# RAG against the machine

A Retrieval-Augmented Generation (RAG) system that answers questions about the
[vLLM](https://github.com/vllm-project/vllm) 0.10.1 codebase. Retrieval uses a
BM25 lexical index built from structure-aware chunks, and answers are
generated by the small local model `Qwen/Qwen3-0.6B`.

## Description

A language model only knows what it was trained on. Instead of putting new
knowledge into the model, RAG lets the model look the information up at answer
time. This project builds that pipeline for a large codebase (thousands of
files) in four stages:

1. **Indexing**: read the vLLM repository, split every Python and Markdown
   file into chunks, and persist a searchable index.
2. **Retrieving**: given a question, return the `k` most relevant source
   locations (file path plus character range).
3. **Augmenting**: read the text of those locations back from the corpus and
   fit it into the model's context window.
4. **Generating**: ask `Qwen/Qwen3-0.6B` to answer the question from that
   context only.

The system is judged on whether it retrieves the right source locations
(recall@k, where a result counts if it is in the same file and its character
range overlaps the reference with an IoU of at least 0.05) and on whether the
answers are grounded in the retrieved text.

| Requirement | Target |
|---|---|
| Indexing time (whole corpus) | at most 5 minutes |
| Retrieval throughput | at most 90 seconds for 200 questions |
| Recall@5 on docs questions | at least 80 % |
| Recall@5 on code questions | at least 50 % |
| Size of any retrieved source | at most 2000 characters |

### Running the full pipeline

```bash
# 1. Build the index (once)
uv run python -m src index --max_chunk_size 2000

# 2. Search a whole dataset
uv run python -m src search_dataset \
  --dataset_path data/datasets/UnansweredQuestions/dataset_docs_public.json \
  --k 10 \
  --save_directory data/output/search_results/UnansweredQuestions

# 3. Score the results with the provided moulinette

uv run python -m src answer_dataset \
  --student_search_results_path data/output/search_results/UnansweredQuestions/dataset_docs_public.json \
  --save_directory data/output/search_results_and_answer/UnansweredQuestions
```

positive, an overlap not smaller than the chunk size, missing files,

## Example usage

Search for one question (output format: `file_path [first:last]`, best result
first):

```bash
uv run python -m src search "How to configure the OpenAI server?" --k 5
# <file_path> [<first_character_index>:<last_character_index>]
# ...
```

Answer one question (prints the answer, then the sources it was built from):

```bash
uv run python -m src answer "How do I load a LoRA adapter?" --k 5
```

Try a different chunk size (this rebuilds the index):

```bash
uv run python -m src index --max_chunk_size 1000 --overlap_size 100
```

Score your own results, for example with a different `k`:

```bash
uv run python -m src evaluate \
  --student_search_results_path data/output/search_results/UnansweredQuestions/dataset_docs_public.json \
  --dataset_path data/datasets/AnsweredQuestions/dataset_docs_public.json
# Recall@1: ...
# Recall@3: ...
# Recall@5: ...
# Recall@10: ...
```

Edge cases are handled with a message instead of a crash:


## System architecture

```
                       INDEXING  (command: index)
  data/raw/vllm-0.10.1
        |  discover_files        (.py and .md, sorted)
        v
  PythonChunker / MarkdownChunker      one list[Chunk] per file
        |  assign sequential chunk_id, validate every span <= max_chunk_size
        v
  tokenize_chunk                       path tokens + symbol tokens + text tokens
        |
        v
  BM25Okapi (rank_bm25)
        |  save_index
        v
  data/processed/{chunks.json, bm25.pkl, meta.json}

                RETRIEVAL AND GENERATION  (commands: search, answer, ...)
  question
        |  tokenize                    same tokenizer as at index time
        v
  Retriever: BM25 scores for every chunk -> stable descending sort -> top-k
        |  chunk.to_minimal_source()
        v
  MinimalSource(file_path, first_character_index, last_character_index)
        |
        |  (answer commands only)
        v
  Generator: re-read the text of each source from data/raw, fit it in the token
             budget, build a chat prompt, run Qwen3-0.6B
        v
  MinimalAnswer / StudentSearchResultsAndAnswer  (JSON)
```

| Component | File | Responsibility |
|---|---|---|
| CLI | `cli.py`, `__main__.py` | Python Fire commands, validation of user input, one place where expected errors become clean messages |
| Data models | `models.py` | The pydantic models of the subject, plus `Chunk` and `IndexMetadata` |
| Chunkers | `python_chunker.py`, `markdown_chunker.py` | Turn one file into chunks with exact character spans |
| Tokenizer | `text_utils.py` | Turn text into BM25 terms; identical for chunks and queries |
| Indexer | `indexer.py` | Orchestrates chunking, tokenizing, BM25 construction and saving |
| Index storage | `file_utils.py` | File discovery, `save_index`, `load_index` with consistency checks |
| Retriever | `retriever.py` | Loads the index once, ranks chunks, batch search with a progress bar |
| Generator | `generator.py` | Builds the context and prompt and runs the model |
| Evaluation | `evaluation.py` | Recall@k with the IoU overlap rule (own testing) |

The central invariant: **row `i` of the BM25 index is `chunks[i]`, and
`chunks[i].chunk_id == i`**. The chunk list is never reordered or filtered
after tokenizing, so a BM25 score can be mapped back to its chunk by position.

## Chunking strategy

Two strategies, because Python code and Markdown pages do not break apart the
same way. Both follow one rule: **keep the largest meaningful structure that
fits in `max_chunk_size`** (default 2000 characters, never above), and split
further only when it does not fit. Every chunk records the exact character
range of the original file it covers, and the chunk text is a slice of the
original file (`source[first:last]`).

### Python files (`python_chunker.py`)

The file is parsed with the standard `ast` module. The AST is used only to find
boundaries; chunk text always comes from the original source.

1. The top-level statements are grouped in source order into three kinds of
   units: classes, functions (including `async`), and runs of consecutive
   other statements (imports, constants, `if __name__ == "__main__":`, ...)
   called module-level groups. Nothing the AST can see is dropped.
2. A **function** that fits is one chunk.
3. A **class** that fits, with all its methods, is one chunk.
4. A class that does not fit is split by method. Each method is its own chunk
   named `Class.method`, and class-level statements (docstring, attributes)
   are grouped the same way as module-level ones.
5. A function, method or group that is still too large is cut into
   consecutive windows of at most `max_chunk_size` characters that overlap by
   `overlap_size` characters (default 100). The last window ends exactly at
   the end of the structure.
6. Spans are line-granular: a unit starts at the first line of its decorators
   (the AST reports the line of `def`, not of the first `@decorator`) and
   ends at the end of its last line. Offsets come from a table of line start
   positions, which sidesteps the AST's column offsets (those count UTF-8
   bytes, not characters).

### Markdown and text files (`markdown_chunker.py`)

1. Headings (`#` to `######`) are found line by line, ignoring lines inside
   fenced code blocks, so a shell comment in a code sample is never mistaken
   for a heading.
2. A heading's section runs from the heading to the next heading of the
   **same or a shallower level**. This makes a section automatically include
   all its sub-sections, so the heading hierarchy is encoded without building
   an explicit tree.
3. Text before the first heading is a *preamble* chunk.
4. A section that fits is one chunk, with its heading inside it (headings carry
   strong retrieval signal).
5. A section that does not fit is split into its own introduction (the text up
   to its first sub-heading) and, recursively, its immediate sub-sections.
   "Immediate" means the shallowest heading level found inside the section, so
   a document that jumps from `#` to `###` still works.
6. Text that is still too large is packed paragraph by paragraph (blank-line
   boundaries) into chunks of at most `max_chunk_size` characters, with the
   same overlap as for code. A single paragraph larger than the limit falls
   back to a hard cut.
7. A file without any heading (plain text) is one preamble, split by
   paragraphs the same way.

### Common guarantees

- Every chunk span is at most `max_chunk_size` characters; the indexer
  re-checks this for all chunks before saving, and the CLI refuses a
  `--max_chunk_size` above 2000 (the moulinette's `max_context_length`).
- Files are read in text mode as UTF-8, and the same string is used for
  parsing, for offsets and for slicing, so offsets are consistent.
- Files that cannot be read or parsed are skipped and reported at the end of
  indexing instead of aborting the run.

## Retrieval method

**BM25** (Okapi variant, via the `rank_bm25` library), chosen over TF-IDF
because it saturates the effect of repeated terms (`k1`) and normalizes for
chunk length (`b`). Chunk lengths vary a lot here, from a one-line constant
group to a 2000-character function.

### Tokenizer (`text_utils.py`)

Questions and source code rarely use the same words: a question may
paraphrase an idea or quote an identifier verbatim. The tokenizer therefore
keeps both:

- Text is split into word-like pieces (letters, digits, underscore).
- Each piece that is an identifier produces the **whole identifier** plus its
  **parts**, split on underscores and on camelCase boundaries, all lowercase.
  `load_lora_adapter` gives `load_lora_adapter`, `load`, `lora`, `adapter`;
  `LoraManager` gives `loramanager`, `lora`, `manager`; `fp8` stays `fp8`.
- Plain words are emitted once. Duplicates are kept, because BM25 uses term
  frequency. Short and numeric tokens are kept (`fp8`, `v1`, `tp` are
  meaningful in vLLM). There is no stop-word list: BM25's inverse document
  frequency already gives common words almost no weight, and words such as
  `for` or `with` are real code.

### What is indexed per chunk

The token list of a chunk is: **file path tokens** (relative to the corpus
root, so `data/raw/vllm-0.10.1/` does not add noise) + **symbol name tokens**
(function, class or section title) + **text tokens**. The path matters because
the best answer to "How to configure the OpenAI server?" is often in a file
named `openai_compatible_server.md`; the symbol name keeps context for chunks
that were split away from their `def` line.

### Ranking

1. The query goes through the same `tokenize` function.
2. `BM25Okapi.get_scores` returns one score per chunk.
3. Chunks are sorted by score, descending, with a **stable** sort: equal
   scores keep ascending `chunk_id` order, so the same query always gives the
   same output.
4. The first `k` chunks are returned as `MinimalSource` objects (relative
   path with forward slashes, first and last character index).

`k1` (default 1.5) and `b` (default 0.75) are options of `index`; they are
baked into the saved BM25 object.

## Answer generation

`generator.py` loads `Qwen/Qwen3-0.6B` with `transformers` (GPU if available,
otherwise CPU).

1. The retrieved spans are read back from the raw files (same text-mode
   reading as the chunkers, so offsets line up) and added in rank order, each
   labelled with its path, until the context token budget (3000 tokens by
   default) would be exceeded.
2. If no context could be read, the model is not called and a fixed fallback
   answer is returned.
3. The prompt is built with the model's chat template. The system message asks
   the model to answer only from the context, to reply with the fallback
   sentence when the context does not contain the answer, not to invent
   function names, file names or options, and to answer in a few sentences.
4. Qwen3's "thinking" mode is switched off (`enable_thinking=False`), because
   a 0.6B model wastes its tokens on it. Decoding is greedy (deterministic),
   with at most 256 new tokens.
5. A failure during generation, or an empty answer, produces the fallback
   answer instead of crashing a long dataset run.

The answer is wrapped in the pydantic models of the subject, so the output
files are always valid `StudentSearchResultsAndAnswer` JSON.

## Design decisions

- **Structure first, size second.** Chunks follow classes, functions and
  headings, and are cut by size only when a structure does not fit. Keeping a
  whole class or section together keeps related text in one retrievable unit.
- **BM25 with a custom tokenizer.** The tokenizer keeps whole identifiers and
  their parts, so both verbatim identifiers and paraphrased questions can
  match.
- **Metadata as tokens, not as text.** The file path and symbol name are added
  to the token list at index time. Chunk text stays an exact slice of the
  file, so the character range reported to the grader is always accurate.
- **Exact spans.** Python spans use line boundaries, decorators included, and
  Markdown spans use heading lines. No span ever exceeds the chunk size.
- **Index on disk.** `chunks.json` (validated with pydantic on load), a pickled
  BM25 object, and `meta.json` written last as the "index is complete"
  marker, with its stale copy deleted before a rebuild. Loading checks that
  the chunk count, the metadata and the BM25 corpus size agree. The pickle is
  only ever loaded from files this program wrote itself.
- **Deterministic ranking.** Stable sort, so ties never change between runs.
- **Validation at the boundary.** The CLI checks user input (the 2000 limit,
  `k`, paths, JSON) and turns expected errors into one-line messages. The
  library classes raise specific exceptions instead of exiting.
- **Fast startup.** PyTorch is imported lazily so commands that do not use
  the model start quickly.
- **Small-model prompting.** Thinking mode off, greedy decoding, short and
  explicit instructions, a fixed fallback sentence, and no model call when
  there is no context.

## Challenges faced

- **From AST line numbers to character offsets.** The AST gives line numbers
  but the subject needs character positions. Solved with a table of line start
  positions. Two traps along the way: decorators sit before the `def` line
  that `lineno` points to, and `col_offset` counts bytes, so spans are kept
  line-granular.
- **Splitting oversized text without breaking the limit.** Overlapping windows,
  paragraph packing and the single-giant-paragraph fallback each had edge
  cases (a final fragment that was dropped, windows that could step backwards
  past the start of their section, loops that could stop making progress).
  These were fixed and checked against the real corpus with an invariant
  script: every span at most the limit, text equal to its slice, full
  coverage.
- **Code fences in Markdown.** Lines starting with `#` inside fenced code
  blocks look like headings. They are skipped, and the line counter must
  still advance on those lines, otherwise every later heading is mapped to
  the wrong line. This bug was found in review, and a regression check on a
  file with code blocks before its headings now confirms heading line
  numbers.
- **Paraphrases versus identifiers.** A question rarely shares words with the
  code it asks about. Solved with the identifier-plus-parts tokenizer and
  path and symbol tokens.
- **A consistent index.** BM25 rows must stay aligned with the chunk list, and
  a half-written index must never be mistaken for a good one: ordered writes
  with `meta.json` last, and consistency checks on load.
- **A CLI that never shows a traceback.** Python Fire turns a bare `123` into
  a number, so the query is converted back to text; every command catches the
  expected errors and exits with a clear message.
- **Startup time.** Importing PyTorch takes seconds, so it is imported only
  inside the generator.
- **A very small model.** Qwen3-0.6B reasons poorly and wastes tokens in
  thinking mode, so the prompt is short and strict, thinking is disabled, and
  there is a fallback answer.

### Known limitations

- Only `.py` and `.md` files are indexed (plain text files would be handled by
  the Markdown chunker if their extension were added).
- Python line offsets are built with `str.splitlines()`, while the AST only
  counts `\n` as a line break. A Python file with an exotic line-break
  character (form feed, `U+2028`, ...) inside a string or comment could get
  shifted chunks. TODO: state whether the corpus scan found affected files
  and whether this was fixed; delete this bullet if it was fixed.
- For Markdown, the shallowest heading level in a file is treated as the top
  level; text before the first heading of that level would be left out if a
  file started with a deeper heading.
- Overlapping windows of one large function can occupy several of the top-`k`
  slots for the same file.
